# Every additional abstraction must pay rent.

- abstraction
- interface
- service layer
- adapter
- factory
- strategy
- framework
- dependency
- configuration option
- database object
- background worker

“最佳实践通常这么做”

不能单独作为引入复杂度的充分理由。

5\. Minimality Contract
=======================

建立一个清晰、简短、可复用的 Minimality Contract。

建议语义如下，但应根据现有仓库组织选择最小落点：

---

## Minimality

Implement only what is required to satisfy:

- current approved architecture;
- current machine-verifiable contracts;
- current invariants;
- current acceptance criteria;
- concrete, observed implementation constraints.

Prefer the smallest implementation that satisfies them.

Do NOT introduce without current justification:

- speculative extension points;
- abstractions with no current consumer;
- generic frameworks for one current use case;
- infrastructure for future stages;
- compatibility layers for versions that do not exist;
- configurable strategies when only one behavior is required;
- indirection whose only justification is possible future reuse;
- dependencies that duplicate existing capability;
- distributed components for hypothetical future scale;
- premature performance optimization without measurements.

When additional complexity appears necessary, record:

1. the current requirement / invariant / acceptance criterion it serves;
2. why the simpler implementation is insufficient;
3. concrete evidence where applicable;
4. the smallest added mechanism;
5. removal/replacement conditions if the complexity is provisional.

\============================================================
6\. 不要把 Minimality 变成“禁止抽象”
===========================

非常重要：

Minimality ≠ 少写代码。
Minimality ≠ 禁止 interface。
Minimality ≠ 禁止设计模式。
Minimality ≠ 禁止模块化。
Minimality ≠ 所有东西都写在一个文件里。

正确判断是：

“当前复杂度是否有实际责任？”

例如：

允许：

- 为真实事务边界建立 repository abstraction；
- 为 Go/Java shared observable semantics 建立 contract test；
- 为现有 plugin permission 建立明确 capability boundary；
- 为真实 Outbox reliability requirement 提供必要实现。

不允许：

- 只有一个实现却为了未来可能第二个实现建立多层 strategy/factory；
- 当前无旧客户端却实现额外 compatibility framework；
- 当前单机阶段为了未来 Loop 2 提前实现 distributed router；
- 没有测量结果就实现复杂 cache / sharding；
- 为一个 endpoint 引入通用 workflow engine；
- 为两个 struct 建造完整 internal framework。

不得把 minimality 简化成 LOC 指标。

- 给出当前 requirement/evidence justification。

Reviewer 不能因为“个人喜欢更简单”否决正确必要的复杂度。
