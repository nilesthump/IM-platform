# Architecture-sensitive technology selection

This execution rule applies to every present and future task, under canonical §2.2 and §2.3. It creates no product contract or alternative architecture authority.

An Agent has no unapproved technology-selection authority. A sufficiently explicit current Frozen Architecture, approved ADR, contracts or Human architecture decision must answer the proposed selection. Long-term decisions must be recorded in Frozen Architecture / approved ADR and independently accepted before product implementation. Categories include programming language, UI/application/client/cross-platform framework, runtime, database/local database, ORM, networking framework, IPC/RPC, state management, plugin runtime, serialization, message queue, cache, storage engine, native bridge, authentication framework, major infrastructure dependency and any core third-party library creating long-term coupling.

If authority does not provide a sufficiently clear answer: stop only affected work, mark `BLOCKED_BY_ARCHITECTURE`, record the smallest question and impact, obtain Architect/Human decision, freeze that decision in the canonical body / approved ADR, add applicable machine guards, obtain fresh independent Review and applicable exact-head hosted CI, then resume product implementation. Complete independent already-authorized work while the blocked portion waits. Never implement first and amend authority after tests to legalize the result.

Familiarity, installed tools, convenience, popularity, fewer lines, a withdrawn attempt, absence of a prohibition, Task Spec text, allowed_paths and CI PASS are not approval. Unprohibited does not mean approved. Chat, handoff, progress, implementation README and source comments alone cannot freeze a long-term decision. Task Specs narrow scope and select already-authorized details; they cannot invent a language, framework, runtime, database, platform strategy, service boundary or protocol. Permitted Go/Java internal structural variation does not confer permission to select a new sensitive technology.

Every Reviewer traces each new sensitive language/framework/dependency to a precise accepted canonical clause or ADR. If this trace fails, Review FAIL. Machine checks supplement this semantic obligation, never replace it.

For client tasks, declare choices in `# Technology Authorization` using `client_framework:`, `client_runtime:`, `client_language:` and `client_dependency:` (one name per line; `TBD` is a blocker, not approval). The checker resolves the canonical client policy and rejects unapproved declarations even when paths permit them or tests pass. Approval comes from authority, never the declaration. Free-form decisions and disguised dependencies still require semantic Review.

Current client policy is canonical §6.1 and ADR-0005: React/TypeScript Web; Tauri/React/TypeScript Desktop with necessary Rust only in clients/desktop/src-tauri; Android Kotlin + Jetpack Compose Mobile; Web/Desktop/shared protocol/plugin/model/Repository/domain/UI direction TypeScript. Mobile equivalent behavior/models/adapters follow the same contracts/fixtures, without mandatory TS SDK reuse. Desktop native SQLite is approved as Tauri + SQLx(SQLite); TypeScript holds Repository/models/transaction intent and Rust only database connections/queries/atomic transaction adapter. Separate tauri-plugin-sql execute() calls cannot emulate a cross-call transaction. Android Studio emulator validates Mobile Android runtime. Only necessary Android SDK/Gradle/Kotlin/Compose engineering identifiers and built-in SDK SQLite follow that choice; no arbitrary Room/ORM/network libs, JS runtime/bridge/codegen or shared native rewrite. Standard package names for the explicitly chosen stack and its type/build bindings are enumerated in canonical policy; this is not permission for other frameworks, state managers, bridges or runtime libraries. No S4 implementation is authorized by reusable SDK direction.
