## Findings

1. **[P1] Atomic materialization/cursor rollback is not observed.** In `message-rollback-and-retry` and `user-rollback-and-retry`, removing `fault: before_commit` from the first step leaves the final expected result unchanged and the oracle accepts both mutations. The user path never materializes friend/Conversation/membership/plugin state at all; it only adds event IDs to an unreturned `seen_events` set and advances `cursor`. The cases therefore cannot prove that a fault rolled back both local data and cursor, or that retry used transactional upsert. This fails SP-A-003/SP-I-003. See `contracts/plugin-api/verify.py` `sync.user` and `sync.message` branches and the attached probe.
2. **[P1] A conflicting duplicate Message payload is silently accepted.** Altering the second duplicate in `gap-out-of-order-duplicate` to a different `content.text` while keeping `(conversationId, seq, messageId, requestId)` fixed yields the unchanged expected result. `run()` stores only `seq -> messageId` and checks collisions only when the message ID differs. The contract README says conflicting identity is rejected, and idempotent materialization cannot silently overwrite or ignore conflicting content. This fails the SP-A-001 duplicate oracle. The gap case also accepts reordering the input so sequence 1 arrives first and no intermediate gap occurs, showing its final-state assertion alone does not observe the gap transition; the separate `gap-stops` case does check a final gap.
3. **[P1] Per-attempt Action authorization is not asserted.** Changing the first Action in `action-retry-audited` to `authorizedAtExecution: false` leaves `last=ALLOWED`, `sideEffects=1`, and `auditAttempts=2`, so the fixture accepts the mutation. The later allowed attempt masks the earlier denial. The runner does not record each attempt's authorization/outcome and therefore cannot establish SP-A-006/SP-A-013's execution-time re-authorization and audit behavior for every attempt.
4. **[P2] Upgrade stage probes are interchangeable.** Changing the `upgrade-fail-migration` input to fail at `snapshot` yields the same expected result and passes. The five failure cases use a single generic `failed` branch and do not observe whether snapshot, migration, each paired health check, and atomic switch happened in order or whether the old version served throughout. SP-A-010's each-step failure requirement is not independently verified.
5. **[P1] Go/Java parity is asserted by repeating one Python oracle.** `golden.json` contains a `profiles` array, but no distinct profile outcome artifacts or independent backend results. `verify()` loops over `go` and `java` and invokes the same `run(copy.deepcopy(case))` for both. This cannot detect divergent Go and Java normalizations, so SP-A-012's identical cross-profile outcomes are not established.

The six accepted mutations above are in the in-memory probe. A seventh mutation reused a Message/request ID at two sequences; the fixture expectation differed, but `run()` itself did not raise `Invalid`, which is a separate indication that identity consistency needs a direct assertion. I did not count it among the six unchanged-expectation failures.
