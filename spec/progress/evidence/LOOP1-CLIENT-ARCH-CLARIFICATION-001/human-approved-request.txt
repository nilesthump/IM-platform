### 2.1 Agent 没有未授权技术选型权

当实现任务涉及下列任一技术决策，而现行 Frozen Architecture、approved ADR、contracts 或明确 Human 指令没有给出唯一或足够明确的答案时：

- 编程语言
- UI framework
- application framework
- runtime
- database / local database
- ORM
- network framework
- IPC/RPC mechanism
- state management framework
- client framework
- plugin runtime
- serialization framework
- message queue
- cache
- storage engine
- native bridge
- cross-platform framework
- authentication framework
- major infrastructure dependency
- 会形成长期架构耦合的核心第三方库

Agent **MUST NOT**：

- 根据“自己熟悉”
- 根据“机器已经安装”
- 根据“最方便”
- 根据“社区流行”
- 根据“代码最少”
- 根据“之前某个失败实现已经用了”
- 根据“Task Spec 没明确禁止”
- 根据“allowed_paths 允许”
- 根据“CI 能通过”

自行做出技术选型。

**未禁止 ≠ 已批准。**

### 2.2 技术栈不明确时的唯一合法流程

发现架构级技术选择缺失时，Agent 必须：

```text
发现技术栈/框架/核心依赖未冻结
              ↓
停止受影响实现
              ↓
标记 BLOCKED_BY_ARCHITECTURE
              ↓
整理最小决策问题与影响范围
              ↓
等待 Architect / Human 明确决定
              ↓
写入 Frozen Architecture / approved ADR
              ↓
独立 Review + applicable CI
              ↓
架构决定正式生效
              ↓
恢复产品实现
```

顺序不得反转。

尤其禁止：

```text
先实现
 ↓
跑通测试
 ↓
再修改 Frozen Architecture 追认
```

这是明确的治理违规。

### 2.3 Architect 决策必须先落入权威层

Architect / Human 给出技术决定后，Agent 不得仅把决定记录在：

- chat
- handoff
- task notes
- progress/current.md
- implementation README
- source comments

然后直接实现。

凡是会影响长期项目技术栈、目录边界、依赖方向或运行时模型的决定，必须先进入适当的权威层：

优先：

1. Frozen Architecture
2. approved ADR / frozen decision
3. 必要的 machine-readable architecture/source checks

然后才能创建或继续实现 Task。

### 2.4 Task Spec 无权自行补充架构决定

Task Spec 可以：

- 收窄实现范围
- 选择已经授权的实现细节
- 指定测试和 acceptance
- 指定 allowed_paths

Task Spec 不得自行发明新的：

- 技术栈
- framework
- runtime
- database
- cross-platform strategy
- service boundary
- public protocol

例如以下逻辑是无效的：

> “Task Spec 写了 Dart，所以 Dart 已被批准。”

如果 Dart 没有先被 Frozen Architecture / ADR / Human architecture decision 授权，则 Task Spec 本身就是违规的。

### 2.5 Reviewer 必须检查“选型来源”

所有新的 architecture-sensitive dependency / language / framework，Reviewer 必须能够回答：

> “它的架构授权来自哪里？”

有效答案必须指向：

- Frozen Architecture 具体条款；或
- approved ADR；或
- Human-approved architecture clarification 已经正式固化的记录。

如果只能回答：

- “Agent 觉得合适”
- “开发机已经安装”
- “之前代码用了”
- “package 很流行”
- “CI PASS”

则 Review 必须 FAIL。

### 2.6 CI 应尽可能机器化这一规则

对于已经冻结的技术栈，应该尽可能增加：

- source allowlist
- forbidden source type
- dependency guard
- architecture negative controls
- path-aware CI assertions

避免未来 Agent 再次静默偏离。

但 CI guard 不能代替架构文档。

顺序仍然是：

**Human/Architect 决策 → Frozen Architecture → Machine Guard → Implementation**
